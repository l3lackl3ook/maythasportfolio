Cloud FinOps & Gemini API Cost Governance

วิศวกรรมควบคุมต้นทุนคลาวด์ — ลดค่าใช้จ่าย Gemini API 73%

Diagnosed runaway LLM token consumption across automated scraping and SEO probes, re-architecting schemas and Celery schedules to cut recurring costs by 73% without losing platform coverage.

วิเคราะห์และแก้ไขปัญหาการใช้ Token สูงเกินความจำเป็นของระบบรัน AI อัตโนมัติ โดยปรับโครงสร้าง Schema และตารางเวลา Celery ใหม่ ลดค่าใช้จ่ายรายรอบลงได้ถึง 73% โดยที่ข้อมูลยังครบถ้วนเหมือนเดิม

−73%
฿3,937.72 ฿1,068.57
Verified in GCP Billing Console · 1–13 Aug 2026 vs 19–31 Jul 2026
  • Output Schema Compression (8,192 → 2,048 Tokens): Replaced verbose free-text JSON outputs with compact, strictly typed Pydantic/Zod schemas, cutting output token overhead by 75%. บีบอัด Output Schema จาก 8,192 เหลือ 2,048 Tokens: เปลี่ยนการสั่งให้ AI ตอบกลับจากโครงสร้าง JSON ขนาดใหญ่มาเป็น Typed Schema ที่กระชับและตรงจุด
  • Content-Hash Diffing & Cadence Alignment: Added SHA-256 content hashing so Celery Beat workers skip re-evaluating unchanged creator profiles and synchronized stale snapshot windows. ตรวจสอบการเปลี่ยนแปลงด้วย Hash & จัดรอบ Celery: ข้ามการส่งโปรไฟล์เดิมที่ข้อมูลไม่เปลี่ยนไปถาม AI ซ้ำ และจัดตารางรันงานเบื้องหลังให้สอดคล้องกัน
  • Automated Budget Circuit-Breakers: Built per-job token ledgers in PostgreSQL that pause non-critical background probes if daily quota thresholds are approached. ตั้งระบบตัดวงจรคุมงบรายวัน (Budget Guards): บันทึกจำนวน Token ที่ใช้จริงลงฐานข้อมูลและชะลองานที่ไม่เร่งด่วนอัตโนมัติหากใกล้ถึงเพดานงบรายวัน

CASE 01 · DATA INGESTION & QUOTA RECOVERY

Meta Graph API 100-Post Pagination & Multi-Lane Fallback

แก้ขีดจำกัด Meta Graph API ดึงได้ 100 โพสต์ & ระบบสลับช่องทางเมื่อติดโควตา

1. Problem Discovered1. ปัญหาที่พบจริง

Social platforms impose strict pagination caps (100 IG Business posts per request) and aggressive HTTP 429 rate limits, causing background workers to stall mid-sync and produce incomplete creator engagement metrics.

การดึงข้อมูลจาก Social API มีข้อจำกัดจำนวนโพสต์ต่อรอบ (เช่น IG Business จำกัด 100 โพสต์/คำขอ) และติด HTTP 429 Rate Limit บ่อยครั้ง ทำให้การคำนวณ Engagement Rate ย้อนหลังไม่สมบูรณ์

2. Architectural Solution2. แนวทางที่เลือกพัฒนา

Separated collection paths by account tier: routed authenticated business profiles through Meta Graph API (100 posts/req batching) with Redis cursor checkpoints, while routing public creator profiles through a free-lane scraper with Bright Data proxy fallback.

แยกช่องทางการดึงข้อมูลตามประเภทบัญชี: ใช้ Meta Graph API คู่กับการเก็บสถานะ Cursor ใน Redis สำหรับบัญชี Business และใช้ช่องทางสำรอง (Fallback) ผ่าน Bright Data เมื่อโควตาหลักเต็ม

3. Engineering Trade-off3. เหตุผลในการตัดสินใจและข้อจำกัด

Proxy fallbacks incur per-GB bandwidth cost. Added an automated byte/request ledger with circuit-breakers so fallback lanes only trigger for active campaign creators.

การสลับไปใช้ Proxy สำรองมีต้นทุนตามปริมาณข้อมูล จึงสร้างตัวคุมโควตา (Budget Guard) ให้เปิดใช้ช่องทางสำรองเฉพาะครีเอเตอร์ที่อยู่ในแคมเปญสำคัญ

4. Measured Test Outcome4. ผลลัพธ์จากการทดสอบใช้งานจริง

Achieved 100 IG Business posts/request and 2.5× post coverage on the free lane during production tests, lifting overall sync completion across 57.5K profiles to 99.2%.

ดึงข้อมูลได้เต็มเพดาน 100 โพสต์/คำขอ สำหรับ IG Business และเพิ่มความครอบคลุมของโพสต์ในช่องทางปกติขึ้น 2.5 เท่าจากการทดสอบจริง

CASE 02 · DATA QUALITY & ENTITY DISAMBIGUATION

Eliminating Brand Affinity False Positives (Urban Revivo vs. Vivo)

แก้ปัญหา AI จำแนกชื่อแบรนด์สับสน (กรณีศึกษา Urban Revivo กับ Vivo)

1. Problem Discovered1. ปัญหาที่พบจริง

Initial keyword and naive LLM matching flagged fashion retailer "Urban Revivo" as smartphone brand "Vivo" due to substring overlap, skewing creator sponsorship history and category affinity scores.

การตรวจจับชื่อแบรนด์แบบ Substring และการถาม AI โดยไม่มีกรอบควบคุม ทำให้โพสต์รีวิวเสื้อผ้า "Urban Revivo" ถูกตีความผิดเป็นมือถือ "Vivo" ส่งผลให้ข้อมูลประวัติสปอนเซอร์คลาดเคลื่อน

2. Architectural Solution2. แนวทางที่เลือกพัฒนา

Implemented a two-stage validation pipeline: (1) strict regex word-boundary & negative-lexicon pre-filtering, followed by (2) constrained Gemini schema validation requiring industry-vertical alignment (Fashion/Apparel vs. Consumer Electronics).

ออกแบบระบบคัดกรอง 2 ชั้น: ชั้นแรกใช้ Regex Word-Boundary ตัดคำซ้อนทับ และชั้นที่สองใช้ Gemini Schema Validation ที่บังคับตรวจความสอดคล้องของหมวดหมู่อุตสาหกรรม (เสื้อผ้าแฟชั่น vs มือถือ)

3. Engineering Trade-off3. เหตุผลในการตัดสินใจและข้อจำกัด

Two-pass checking adds minor compute overhead on new captions; mitigated by caching verified brand-entity pairs in PostgreSQL.

แลกกับการประมวลผลเพิ่มขึ้นเล็กน้อยในโพสต์ใหม่ ซึ่งชดเชยด้วยการทำ Cache ผลลัพธ์การจับคู่แบรนด์ที่ตรวจสอบผ่านแล้วลงใน PostgreSQL

4. Measured Test Outcome4. ผลลัพธ์จากการทดสอบใช้งานจริง

False-positive brand attribution dropped from 18.4% to under 1.2% on audited gold-set samples, making brand affinity filters reliable for sales pitches.

ลดอัตราการจับคู่แบรนด์ผิดพลาด (False Positive) จาก 18.4% ลงมาเหลือต่ำกว่า 1.2% จากชุดข้อมูลตรวจสอบจริง

CASE 03 · WORKFLOW ARCHITECTURE & SECURITY

Zero-Login CEO Lead Assignment via HMAC-Signed Gmail Links

ออกแบบระบบให้ CEO กด Approve แจก Lead จากใน Gmail โดยไม่ต้องล็อกอินซ้ำ

1. Problem Discovered1. ปัญหาที่พบจริง

When inbound leads arrived from website forms, requiring the CEO to open a browser, log into the CRM, and manually assign a sales rep created response delays during busy executive hours.

เมื่อมี Lead ลูกค้าติดต่อเข้ามา การที่ผู้บริหารต้องเปิดเว็บ ล็อกอินเข้า CRM แล้วกดเลือกเซลส์ด้วยตัวเองทุกครั้ง ทำให้เกิดความล่าช้าในการส่งต่อลูกค้าให้ฝ่ายขาย

2. Architectural Solution2. แนวทางที่เลือกพัฒนา

Built an HMAC-SHA256 token signer (leadId.salesEmail.assignerEmail.exp) embedded directly into Nodemailer HTML buttons sent to Gmail. Clicking a sales rep button verifies the cryptographic signature, checks RBAC permissions, assigns the lead, and logs the audit trail.

สร้างระบบแนบลิงก์เข้ารหัส HMAC-SHA256 ลงในปุ่มอีเมลที่ส่งเข้า Gmail ของผู้บริหาร เมื่อกดปุ่มชื่อเซลส์ในเมล ระบบจะตรวจลายเซ็นดิจิทัล ตรวจสิทธิ์ RBAC แจกงานให้เซลส์ทันที และบันทึก Audit Log

3. Engineering Trade-off3. เหตุผลในการตัดสินใจและข้อจำกัด

Set a 14-day token TTL so unread weekend emails remain actionable, while enforcing idempotent assignment checks so accidental double-clicks do not duplicate notifications.

กำหนดอายุ Token ไว้ 14 วันเพื่อให้เมลที่ค้างช่วงวันหยุดยังกดอนุมัติได้ พร้อมทำ Idempotency Check ป้องกันการกดปุ่มซ้ำแล้วส่งแจ้งเตือนซ้อน

4. Measured Test Outcome4. ผลลัพธ์จากการทดสอบใช้งานจริง

Reduced executive lead-triage time from minutes to under 5 seconds directly inside mobile Gmail, speeding up sales first-response time.

ลดขั้นตอนการอนุมัติและจ่ายงานของ CEO เหลือไม่ถึง 5 วินาทีผ่านแอป Gmail บนมือถือ ช่วยให้ทีมขายติดต่อลูกค้าได้ไวขึ้น

CASE 04 · METRIC ACCURACY & COST GOVERNANCE

Engagement Rate (ER) Normalization & −73% Token Budgeting

การปรับมาตรฐานสูตรคำนวณ ER ข้ามแพลตฟอร์ม & การลดต้นทุน AI 73%

1. Problem Discovered1. ปัญหาที่พบจริง

Raw scraped metrics across TikTok, IG, and Facebook used inconsistent denominators (views vs. followers) and outlier viral posts distorted average ER, while 8,192-token Gemini probes inflated cloud bills.

ข้อมูลดิบจากแต่ละแพลตฟอร์มใช้ฐานคำนวณ ER ต่างกัน และโพสต์ที่เป็นไวรัลบางโพสต์ดึงค่าเฉลี่ยเพี้ยน ขณะเดียวกันการส่งข้อมูลเข้า Gemini แบบไม่จำกัดขนาด Schema ทำให้ค่าใช้จ่ายสูง

2. Architectural Solution2. แนวทางที่เลือกพัฒนา

Standardized platform-specific ER formulas with outlier trimming and post-count confidence flags, while compressing Gemini output schemas from 8,192 to 2,048 tokens with SHA-256 diffing.

แยกสูตรคำนวณ ER ตามธรรมชาติของแต่ละแพลตฟอร์มพร้อมตัดค่าเพี้ยน (Outlier) และบีบอัด Gemini Output Schema จาก 8,192 เหลือ 2,048 Tokens ร่วมกับการเช็ก Hash ก่อนรัน

3. Engineering Trade-off3. เหตุผลในการตัดสินใจและข้อจำกัด

Requires storing historical post snapshots in PostgreSQL rather than only summary averages, trading cheap disk storage for verifiable metric traceability.

ใช้พื้นที่จัดเก็บ Snapshot รายโพสต์ใน PostgreSQL เพิ่มขึ้นเล็กน้อย เพื่อแลกกับการตรวจสอบย้อนกลับได้ (Traceability) ว่าตัวเลข ER คำนวณมาจากโพสต์ใด

4. Measured Test Outcome4. ผลลัพธ์จากการทดสอบใช้งานจริง

Cut Gemini API billing by 73% (฿3,937.72 → ฿1,068.57) and eliminated distorted ER spikes in client campaign shortlists.

ลดค่าใช้จ่าย Gemini API ลง 73% จากบิลจริง และทำให้ตัวเลข ER ที่นำไปเสนอขายลูกค้ามีความน่าเชื่อถือและตรวจสอบย้อนกลับได้
